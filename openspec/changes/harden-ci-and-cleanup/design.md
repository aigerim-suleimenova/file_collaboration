## Context

See proposal.md (Why) for the defects. These facts about the current code shape the approach:

- **Backend:**
  - `app/core/config.py` uses pydantic-settings with `env_file=".env"` and `env_ignore_empty=True`. It already has `_check_default_secret()`, which raises when a value equals `"changethis"` outside `local`, but `SECRET_KEY` defaults to `secrets.token_urlsafe(32)`, so that check never fires.
  - `app/core/db.py` creates the engine with no timeouts.
  - The CORS origins in `app/main.py` are a hard-coded localhost list; `settings.all_cors_origins` exists but is unused.
- **Alembic:**
  - `alembic.ini` points at `app/alembic`, whose `env.py` already targets `SQLModel.metadata` and reads `settings`. `backend/alembic/` is an unused duplicate.
  - There are 5 revisions; the chain breaks at `update_file_schema_001`.
  - The installed Alembic (1.12.1) has `alembic check`.
  - `script.py.mako` doesn't import `sqlmodel`, but autogenerated SQLModel columns use `sqlmodel.sql.sqltypes.AutoString`.
- **Containers:**
  - `python:3.11-slim` has no `curl`.
  - `.dockerignore` excludes `.env`, `.venv` and `logs/`, but not `scripts/` or `tests/`.
- **Frontend:**
  - `api.js` uses `baseURL: '/api/v1'`.
  - `vite.config.js` proxies `/api/v1` (with `ws: true`) to the hard-coded `http://localhost:8000`.
  - There's no ESLint config, but `eslint`, `eslint-plugin-vue` and `@vue/eslint-config-prettier` are already dev dependencies.
- **CI:** one workflow, `deploy.yml` (see proposal). The backend tests use in-memory SQLite (`tests/conftest.py`).

## Goals / Non-Goals

**Goals:**
- A clean clone works three ways: `docker compose up`, CI, and a standalone frontend + backend deployment. Each path is checked by something automated or by a scripted manual check.
- One way to create the schema, used by every environment.

**Non-Goals:**
- Frontend unit or E2E tests (Vitest, Playwright): a later change.
- Raising the coverage target. CI reports coverage without a threshold for now.
- Keeping data from existing databases. The user confirmed there is no deployed data to keep.
- Revising `backend/scripts/run.sh`, `setup-dev.sh` or `deploy.sh` beyond removing references to deleted files.
- Changing the `POSTGRES_PASSWORD` default (`12345678`), which is a dev-only value.

## Decisions

### 1. `/health` at the root, with a cheap database probe
- **Route:** `GET /health` is defined in `app/main.py`, outside the `/api/v1` prefix, because `railway.json` and the Dockerfiles already call `/health`.
- **Probe:** it runs `SELECT 1` through the engine in a threadpool and returns 200 or 503 with the fixed bodies in the spec. Exceptions are logged on the server and never returned.
- **Timeouts:** the engine gets `pool_pre_ping=True` and `connect_args={"connect_timeout": 3}` (Postgres only), so a database outage gives a 503 quickly instead of hanging.
- **Docker health check:** `python -c` with `urllib.request.urlopen("http://localhost:${PORT:-8000}/health", timeout=3)`, using only the standard library.
- *Alternatives:* installing `curl` in the image (bigger image for no gain); a health check without the database probe (would report healthy while every request fails).

### 2. `SECRET_KEY` default becomes `"changethis"`
Change the default to `"changethis"` so the existing `_check_default_secret` does its job: a warning in `local` and a `ValueError` in `staging`/`production`.
- An empty value is treated as unset by a `field_validator`, so it's also refused in deployments. (`env_ignore_empty=True` is configured, but pydantic-settings 2.1.0 doesn't apply it; this was found during implementation.)
- Local restarts keep the same key, so tokens stay valid.
- Compose's dev backend runs with `ENVIRONMENT=local`, so it needs no secret.
- *Alternative:* keep a random key in local mode. Rejected because every `--reload` logs everyone out, which is the reported problem.

### 3. One baseline migration, generated and then reviewed
1. Delete the 5 files in `app/alembic/versions/` and the unused `backend/alembic/` folder.
2. Add `import sqlmodel` to `script.py.mako`.
3. Generate `0001_baseline` with `alembic revision --autogenerate` against an empty Postgres database.
4. Review it by hand: tables, indexes, FK `file.owner_id → user.id` with `ON DELETE` matching the model, `file.yjs_state` as `LargeBinary`, and a `downgrade()` that drops in reverse order.

**Validation:** CI runs `alembic upgrade head && alembic check && alembic downgrade base && alembic upgrade head` against its Postgres service. A pytest test (`tests/test_migrations.py`, marked `integration`) does the same when `TEST_POSTGRES_URL` is set, and is skipped otherwise, so local SQLite runs stay fast.

*Alternative:* repair the broken revisions in place. Rejected: there is no data to keep, and five half-overlapping revisions are harder to review than one.

### 4. Single start script for all deploy paths
`backend/scripts/start.sh`:

```sh
set -eu
alembic upgrade head
exec uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8000}" "$@"
```

- Both Dockerfiles use `CMD ["sh", "scripts/start.sh"]`, keeping the single-worker comment.
- Compose dev uses `command: sh scripts/start.sh --reload`.
- `railway.json` uses `cd backend && sh scripts/start.sh`.
- Because of `exec`, uvicorn becomes PID 1 and receives SIGTERM, so collaboration state is saved on shutdown. That behaviour was verified in the previous change.
- `init_database.py` is deleted. It only created tables (now done by migrations) and a superuser from settings that aren't documented anywhere. `setup-dev.sh` now calls `alembic upgrade head`.

### 5. Local compose fixes
- **db:** remove the `init_database.py`, `pg_hba.conf` and `postgresql.conf` mounts and the custom `command`. The default `postgres:15-alpine` setup is enough for development. Delete the three root `.conf` files.
- **backend:** `POSTGRES_PORT=5432` and `command: sh scripts/start.sh --reload`. The `./backend:/app` bind mount stays for hot reload.
- **frontend:** set `VITE_PROXY_TARGET=http://backend:8000` and drop the unused `VITE_API_BASE_URL`, so the browser stays same-origin through the dev proxy. `vite.config.js` reads `process.env.VITE_PROXY_TARGET || 'http://localhost:8000'` for both proxy entries.

### 6. Frontend API base and CORS
- **API base:** `api.js` uses `` baseURL: `${(import.meta.env.VITE_API_BASE_URL || '').replace(/\/$/, '')}/api/v1` ``.
- **Collaboration URL:** `VITE_COLLAB_WS` keeps its own setting (it was added in the previous change). Its default is still derived from `location`.
  - When `VITE_API_BASE_URL` is set and `VITE_COLLAB_WS` isn't, the default is derived from `VITE_API_BASE_URL` (`https:` → `wss:`) + `/api/v1/collab`.
  - Otherwise it stays `location`-based. This makes a standalone deploy work with one variable.
- **CORS:** `app/main.py` uses `settings.all_cors_origins`, plus `http://localhost:3000` and `http://127.0.0.1:3000` when `ENVIRONMENT == "local"`. Methods add `PATCH`, and headers stay `*`.
- **Production image:** `frontend/Dockerfile.prod` declares `ARG VITE_API_BASE_URL` and `ARG VITE_COLLAB_WS`, with `ENV` before `npm run build`. `docker-compose.prod.yml` passes them under `build.args` and drops the ineffective runtime `environment`.

### 7. Backend tests: fake S3, real auth
- **conftest:** add a `fake_s3` fixture that monkeypatches `app.services.s3_service.s3_service` (and the names imported from it in `routes/files.py`) with an in-memory dict that implements `upload_file`, `download_file` and `delete_file`. Check the exact method names when implementing. Users are created through `crud.create_user` so login can work with real bcrypt.
- **New test modules:**
  - `test_auth.py`: signup; login success; wrong password → 400/401 as the route defines; `/users/me` without a token → 401/403.
  - `test_files.py`: upload, list, get, update content, delete; user B gets 404 for A's file on get, content, update and delete.
  - `test_health.py`: 200, plus 503 with the engine's `connect` monkeypatched to raise.
  - `test_config.py`: `Settings(_env_file=None, ENVIRONMENT=..., SECRET_KEY=...)` for each `runtime-configuration` scenario.
  - `test_cors.py`: preflight with allowed and unknown origins.
- The `test_migrations.py` described in Decision 3.

### 8. CI workflow shape
`.github/workflows/ci.yml` replaces `deploy.yml`. Trigger: `push` on `prod` and `main`, plus `pull_request`. Jobs:

- **backend** (Python 3.11; `services.postgres: postgres:15-alpine` with a health check):
  - `pip install -r requirements-dev.txt`;
  - `flake8 app tests`;
  - the Alembic sequence from Decision 3 (with `POSTGRES_*` env pointing at the service);
  - `pytest --cov=app --cov-report=term-missing`, with `TEST_POSTGRES_URL` set so the migration test runs.
  - pytest exits 5 when it collects no tests. That counts as a failure, and the step doesn't mask it.
- **frontend** (Node 20, `npm ci`): `npx eslint src --ext .vue,.js` (no `--fix`), then `npm run build`.
- **docker** (needs backend and frontend): `docker build -f backend/Dockerfile.prod backend` and `docker build -f frontend/Dockerfile.prod frontend`.

No step uses `|| true`, `|| echo` or `exit 0`. `deploy.yml` also uploaded build artifacts, which isn't needed and is dropped. The README gets a status badge for `ci.yml` on `prod`.

### 9. ESLint config
- `frontend/.eslintrc.cjs` uses `root: true` and `env: { browser: true, es2022: true, node: true }`.
- It extends `plugin:vue/vue3-recommended`, `eslint:recommended` and `@vue/eslint-config-prettier`, with `parserOptions.ecmaVersion: 'latest'` and `sourceType: 'module'`.
- **Fixing findings:** errors are fixed in source. Purely stylistic rules that conflict with the existing code style can be turned off in the config, with a comment explaining why. Rules about correctness (for example `no-undef`, `no-unused-vars`, `vue/no-mutating-props`) stay errors.
- `package.json` `lint` becomes `eslint src --ext .vue,.js`, plus a separate `lint:fix`.

## Risks / Trade-offs

- **[ESLint may report a lot in the 1,000-line Vue files]** → Mitigation: fix errors and allow warnings. If errors are too many to fix in one session, stop and report the count. Don't loosen correctness rules (see Decision 9).
- **[`alembic check` false positives]** (for example server defaults or type variants) → Mitigation: review the generated baseline and set `compare_type=True` deliberately. If a difference can't be avoided, fix the model or migration, never the check.
- **[A deployed backend now refuses to start without `SECRET_KEY`]** → This is intended, and the error message says what to set. It's documented in `docs/deployment.md` and the proposal's Impact section.
- **[Migrations run on every container start]** → `alembic upgrade head` does nothing when the schema is current. It runs before uvicorn and inside the single-worker process model, so there is no concurrent-migration race.
- **[The fake S3 can drift from the real `s3_service`]** → Mitigation: the fake implements only the methods the routes call, with the same signatures, and a test checks those names exist on the real class.
- **[Deleting docs loses information]** → Mitigation: any still-correct fact from the seven deployment docs goes into `docs/deployment.md` before deletion, and git history keeps the originals.

## Migration Plan

1. Merge this change. CI runs on the PR and must pass.
2. Any existing development database: drop the compose volume (`docker compose down -v`) or run `alembic stamp head` if the schema already matches. There is no deployed data, as the user confirmed.
3. Deployments: set `SECRET_KEY`, `ENVIRONMENT=production`, `FRONTEND_HOST` and `BACKEND_CORS_ORIGINS` on the backend. Build the frontend with `VITE_API_BASE_URL` (and optionally `VITE_COLLAB_WS`).
4. Rollback: revert the merge commit. The old migration chain didn't work on fresh databases anyway.
